Haxe in Haxe · The long version

How we got here

Porting the Haxe compiler from OCaml to Haxe, holding it to byte-identical output, making it fast, and then writing a backend for it. What we tried, what worked and what didn't.

Home Playground Download Benchmarks

Written 9 October 2026. Every number below comes from the repository: its Git history, test/TESTING.md, bench/README.md and the other notes it cites.

The Haxe compiler is written in OCaml. The compiler running on the front page is a port of it written in Haxe. That port parses, types and filters Haxe programs and writes HXB archives that match the OCaml compiler's byte for byte. It runs macros in its own port of the Eval interpreter, and it is compiled to C by a backend that is also written in Haxe. The resulting native binary compiles the port's own source a little faster than the OCaml compiler does.

This is the long version: the order things happened in, the dead ends, and what we would do the same way again.

Who “we” is. The port was written by Claude, Anthropic's AI model, working in this repository with its owner, Ben Merckx. The repository's ground rules (AGENTS.md) set the scope and the bar. Much of the work ran as many sub-agents in parallel, each in its own Git worktree on its own branch, merged back after validation. The August and September commits are the owner's groundwork. From 7 October on, the history is Claude's: 198 commits in roughly 48 hours, out of 248 in total.

1. The goal, and a strict oracle

The brief was narrow on purpose. Port the compiler in haxe/src (a Git submodule pinned at upstream commit b10fa6e) to Haxe in src/, one module per upstream module, and stay close: same declarations, same branch order, same exceptions and error messages, same data layout wherever possible. Redesigning was out of scope. A faithful translation can be checked against its source line by line, and a redesign can't.

The first functional target was not JavaScript or C++. It was HXB, Haxe's binary module format. An HXB archive is a ZIP file with one .hxb member per module. Each member serializes the typed AST after typing and the cross-target filters have run, but before any target generator touches it. Emitting HXB needs the whole front end (parsing, module loading, typing, finalization and filtering) and no code generator. That makes it the smallest output that still exercises everything that is hard about a compiler.

It also makes a very good oracle. AGENTS.md defines conformance as:

the same normalized ZIP member-name set and byte-for-byte equality of every uncompressed .hxb member payload for the same effective invocation.

The container is ignored: timestamps, member order and compressor output don't count. Everything inside a member counts: the order of the string pool, every variable id, every position, every piece of metadata. A port can't pass by producing something equivalent. It has to make the same decisions in the same order as the original.

The reference is the compiler built from the pinned submodule (make -C haxe haxe), never a system Haxe. That rule turned out to matter. In September there was no OCaml toolchain in the environment, so drafts could only be run against an installed Haxe 5.0.0-preview.1. Its standard library already differed from the pinned one: it rejected StringMap.size(), which the pinned std declares. Until 7 October, “conformance” could not be measured at all.

2. A false start, then a real translation

The repository's first commits (25 August, 41 of them in one night) are a hand-written bootstrap compiler. It had its own recursive-descent grammar, its own tokenizer and its own HXB writer, and it lowered language features by hand, one commit at a time: “lower key value for loops”, “lower simple inline local functions”, “type and serialize try catch expressions”.

The night ended on a note that explains why this approach couldn't reach the bar. Upstream's pattern matcher allocates temporary variables, and every later variable id shifts with them:

The current allocation stream first diverges in haxe.CallStack's complex enum-pattern lowering: upstream allocates matcher temporaries which the port does not yet create, shifting later IDs […] Implement matcher parity; never seed or offset the global counter to hide this gap.

With a byte-exact oracle, reimplementing a behaviour means reimplementing every allocation it makes along the way. The only practical way to do that is to translate the original. On 4 September the project switched to translation first. One commit added 126 draft Haxe files covering 124 upstream .ml modules (18.5k inserted lines), and they compiled the same day. The first run of the translated pipeline reached 22 modules of the Basic fixture and then died with Cannot call null.

Two checkpoints in September got Basic, Int64Basic and then TryCatch through to HXB, fixing several OCaml-semantics bugs of the kind described in the next section.

On 7 October the last hand-written pieces on the main path were replaced by mechanical translations of hxbWriter.ml, grammar.ml and the lexer's token rules. The parser corpus went from 1,339 to 1,355 of 1,366 upstream files. The reference compiler was built at last, and Basic matched it byte for byte on all 22 HXB members.

3. OCaml semantics that leak into bytes

Most payload differences didn't come from wrong logic. They came from places where upstream quietly relies on how OCaml behaves. A few kinds came up again and again.

Evaluation order

OCaml evaluates constructor, tuple and function arguments right to left. Haxe evaluates left to right. When the arguments allocate variables, the order shows up in the ids, and the ids are in the HXB. Upstream's Texpr.map_expr_type contains:

(* haxe/src/core/texpr.ml: the initializer is mapped before the variable *)
{ e with eexpr = TVar (fv v, match eo with None -> None | Some e -> Some (f e)); ... }

The port spells the order out:

// src/core/Texpr.hx
case TVar(v,eo): var eo = eo == null ? null : f(eo); def = TVar(fv(v),eo);

The same fix was needed in the inliner, in exception lowering (catchesToIfs), and in the pattern converter, where make e :: loop el tl types the tail first. It also showed up in error text. The “Recursive type” message is built with sprintf, whose arguments OCaml also evaluates right to left. Printing a constrained monomorph has a side effect on how it prints the next time, so the port has to print the field type first to produce the same message.

Hash table iteration order

OCaml's Hashtbl iterates in an order that depends on its hash function, and that order reaches the output: in the macro interpreter's tables and, later, in display results. The port has core.ds.OcamlHashtbl, which reproduces OCaml's bucket layout and resizing, and core.ds.OcamlHash, which reproduces caml_hash for the key shapes that occur. One bug here took a while to find. OCaml hashes the tagged integer 2n+1, not n, so keys 1 to 5 came out as 3, 1, 4, 2, 5 instead of upstream's 1, 4, 5, 3, 2.

// src/core/ds/OcamlHashtbl.hx: caml_hash mixes Val_long(n) = 2n+1
public static function hashInt(n:Int):Int {
	var h = mixWord(0, (n << 1) | 1);
	...

Physical equality

The HXB writer decides whether to write a position's file name in full with p.pfile != pw.p_file, which is OCaml's physical inequality. Positions created by macros carry freshly decoded strings, so upstream writes them in full even when the text is equal. The port needs a reference comparison on strings (StrTools.physNeq). JavaScript has no string identity, which is one reason 10 macro cases could never match on the JS build. The C backend had the same issue until it compared string pointers.

Immutable lists versus mutable arrays

Upstream prepends to immutable lists. Translated as arrays, the same code mutates shared data:

  • Types aliased their declaration's metadata array and unshifted @:enum into it. A second --next compilation then saw the change and printed 133 deprecation warnings at unknown positions.
  • Filters iterated the live field arrays, so fields added by local_statics were filtered a second time. Upstream iterates a snapshot by construction.
  • The parallel DCE and analyzer unshifted into metadata arrays that other threads were reading. Upstream needs no lock because its lists are immutable. Without -D disable-parallelism, 7 of 160 small cases failed with “Null access .meta”.

Numbers and text

  • Int32 literal parsing used a Float accumulator seeded with an Int, which wrapped on Eval. Separately, negating INT_MIN after wrapping gave +2147483648 on hosts with unbounded integers (JS).
  • OCaml's float_of_string skips underscores, reads the whole string and accepts hex, nan and inf (core.ds.OcamlFloat), so 12.3_4 is not 12.3. string_of_float prints 0.. The JSON printer tries %.16g and falls back to %.17g.

The type system as a safety net

Early drafts used Dynamic for many OCaml records and tuples. In Haxe, reading a misspelled field of a Dynamic silently gives null. find_array_read_access returned a record with fields field, type, ret, index and value, but the caller read key and cf, so a[k] += v on an abstract with @:arrayAccess crashed. Upstream's unit tests found that one. After it, three passes replaced the remaining structured Dynamics with typedefs that follow upstream.

Exceptions as control flow

Upstream uses exceptions the way OCaml programmers do: Not_found, Exit, parser backtracking. Compiling the 32-module stdlib workload throws about 119,000 of them. Cheap in OCaml, they were expensive on every Haxe target we tried, as the next sections show.

4. The harness, and the first green day

test/conformance.py runs every case with the pinned reference and with the port, then checks four things: the same member set, identical uncompressed payloads, that the reference can load the port's archive through --hxb-lib without the case's class path (so nothing is missing), and that the port run from source matches the port run from an Eval HXB archive. Cases the reference rejects must be rejected by the port too.

make -C haxe haxe                                   # the pinned reference
HAXE_REFERENCE=haxe/haxe python3 test/conformance.py -j 8

The cases come from test/discover-cases.py. It classified 543 upstream configurations under tests/misc/eval and tests/optimization. 147 were included; the rest were recorded with a reason (306 only have compile-fail configurations, 67 create a macro context, 10 are rejected by the reference, and so on). Together with a smoke inventory and fixtures, that makes 282 cases.

Two details mattered from the start. Every invocation uses -D disable-parallelism, because with parallel filters the reference takes variable ids from a shared counter and doesn't produce the same output twice itself. And the reference gets the checkout's haxe/std explicitly, or its built-in std path leaks into serialized positions.

Running the port on Eval was slow, so the harness was switched to the port compiled to HashLink, an order of magnitude faster. It also surfaced bugs Eval had hidden: HashLink doesn't pad missing optional arguments in dynamic calls, and labeled OCaml arguments like ~static:true had been translated as positional ones.

The day the reference became available, 7 October, ended with 275 of 275 accepted cases byte-identical and all 7 expected failures rejected. The last diffs were a mutable TLazy (upstream's is a ref, so resolving it updates every holder), two more right-to-left orders, and qualified metadata matches.

5. Macros: porting an interpreter

Haxe macros run in Eval, an interpreter inside the compiler. A port that can't run macros can't compile most real code, including its own source. Its standard library uses macros. So the next milestone was translating macro/eval/*.ml (value model, hashing, the “JIT” that turns typed expressions into closures, prototypes, encoders and decoders, the standard library natives), macroApi.ml and macroContext.ml.

This job was split across several agents. The history shows eight “WIP” translation checkpoints within seven minutes, then one integration commit. On its first run, 12 of 67 macro-context cases were byte-identical. Twenty minutes later all 66 relevant ones were. (The 67th sets its own --hxb output, so it isn't a conformance case.) The remaining bugs were the ones described above: physical string comparison, NUL bytes truncating HashLink StringMap keys in the string pool, right-to-left pattern typing, and filters seeing their own additions. Shortly after, the port could also run programs with --interp and --run. On 268 cases the exit code, stdout and stderr were identical to the reference's. There were 4 known differences, such as the exit code of a failed process spawn (a host-runtime detail) and a timing race in one test.

The macro port is about 20,000 lines of Haxe (src/macros). The debugger, libuv and mbedtls were left out at first and fail explicitly. Faking success is against the rules. TLS and libuv came back later, for the C build.

AGENTS.md also asks for host execution: compile the port to an Eval HXB archive with the pinned compiler, run haxe.Main from it with --hxb-lib, and check that the output matches the source-run port's. That works, and the harness checks it on every case. It is also a useful reminder of what an interpreter on an interpreter costs. Compiling the port's own source this way takes 1,885 s of CPU against the reference's 5 s, about 373 times slower.

6. Making it fast enough on existing targets

Haxe compiles to many targets, so the obvious next step was to compile the port with the reference compiler to each of them and measure. bench/run.py only counts a run if its archive matches the reference's. The first rounds measured the “stdlib” workload (32 standard library modules as roots):

Getting every target to run correctly took patches to the targets themselves:

  • HL/C: the pinned compiler's hl2c crashed on one kind of Dynamic field read; bench/hl2c-virtual-field-cast.patch fixes it.
  • C++: release builds crashed or hung at random, in the string hash, the GC and on collected objects. The cause was hxcpp's multi-threaded GC marking (debug builds mark on one thread, which is why they never crashed). bench/hxcpp-single-thread-mark.patch turns it off.
  • Go: the hx2go custom target needed a source patch and five post-processing scripts (for example, a break inside a try left the whole try body). With all that it passed every case, and it was still the slowest build.

Then came the performance work, in rounds, each one measured with callgrind or perf before changing anything. In rough order of impact:

  1. Exceptions without stack traces. Control-flow exceptions are thrown as shared instances, and stack traces are only recorded when OCAMLRUNPARAM=b is set, as in OCaml. On HashLink, throwing through hl.Api.rethrow skips the native stack capture. That capture alone had been 80% of the HL/C run.
  2. The GC trigger. libhl starts a full, non-generational mark after every 20% of heap growth, so a heap full of typed modules was marked over and over. GcPolicy collects relative to the heap size after the last major collection instead.
  3. Records as classes. Anonymous structures became @:structInit classes and Dynamic parameters were typed, which helped HashLink a little and the JVM a lot.
  4. A patched allocator. bench/libhl-allocator.patch grew over several rounds: larger fixed-size classes, zeroed pages that aren't zeroed twice, inline bump allocation in generated code, batched slice refills, and keeping swept pages for reuse.
  5. Fewer closures. HashLink allocates every local function when its definition runs, whether it is called or not. One analyzer function made 14 allocations per call before doing anything. Helpers that are only called became inline, first in hot functions and then across every package.

Some things didn't work and were dropped, each with its numbers recorded:

  • A generational GC for HL/C. Sticky mark bits, an arena with a byte-per-granule remembered set, and a write barrier emitted by a patched hl2c. It passed the whole conformance suite even with a 1 MB nursery, and it was slower: 0.42 s of user time on stdlib against 0.32 s, and 35–60% slower on the self-compile with a 32–128 MB nursery. The patches are kept in bench/experiments/generational-gc.
  • Bigger allocation slices, skipping the zeroing of pointer-free slices, populating GC chunks at mmap, -O3, -march=native and static linking all made no measurable difference. Transparent huge pages cost 2–3 s of system time on the self-compile, because page faults compacted memory synchronously, so they became opt-in.

At the end of the second pass, HL/C was 1.3× the reference single-threaded. What remained was mostly the runtime: allocation and GC marking were over half the instructions, and live data was about 2.5× the reference's. libhl's collector is conservative and non-generational. We weren't going to win that with more patches to someone else's runtime.

7. Writing our own backend

We also wanted the compiler in a browser, so the next experiment was compiling HL/C's output to WebAssembly with Emscripten. It produced identical archives and showed two problems. The module was 51.5 MB (Binaryen's --spill-pointers, needed so libhl's conservative stack scan can see pointers in wasm locals, grew it from 30.6 MB). And there was a stall of about 20 seconds that had nothing to do with the work.

The stall turned out to happen at exit: hello finished in 2–3.4 s, and then Node waited until about 27 s for optimizing compiles already running on background threads. The 10 largest functions were 45% of the module. All of them contained hl_trap, which is setjmp, and Emscripten's setjmp lowering stores every live local around every call (one setjmp made a synthetic function 26× larger). Marking the largest functions baseline-only through an experimental V8 section cut the self-compile from 25–31 s to 17.5–18 s, but that is a workaround, not a design.

So we wrote down a go/no-go for a backend of our own (bench/WASM-BACKEND.md): one typed IR, lowered from the filtered typed AST that HXB serializes, feeding a WasmGC emitter and a C emitter. The prototype covered a small subset and two benchmark programs, and measured every route we could think of:

What the measurements said:

  • C in linear memory ran as fast as WasmGC on Node, needed no pointer spilling, and shares one GC and one set of semantics with the native build. One runtime then serves both.
  • Never lower try to setjmp on wasm. The C emitter wraps it in RT_TRY macros: setjmp natively (0.027 s for 667k throws), and C++ try/catch when Emscripten compiles the file as C++, which becomes wasm exception handling. For a 40-call test function that was 3.3 KB of wasm instead of 80.7 KB.
  • OCaml as a target was the fastest native route, but wasm_of_ocaml's 31-bit int forces boxed Int32 for Haxe's Int, and it was slower than our own routes on wasm.
  • tcc compiles C 26× faster than gcc -O2, and its code is about 1.7× slower. That makes it the development compiler, with gcc for release builds.

We chose C first. The design note estimated the full lowering, runtime and std as “a multi-week project”. It went faster, mostly because the test program and the test suite already existed. On the morning of 9 October the lowering grew from the subset to the whole port (erased generics with boxing at the boundaries, strings, floats, anonymous structures, Dynamic, closures, exceptions, optional arguments): 7,394 functions and 199 runtime natives, 16 MB of C that tcc compiles and links in under a second. Ten minutes after the first conformance case passed on the tcc build, all 282 did. Less than half an hour later the gcc -O2 build was level with the reference on the self-compile (4.96 s against 4.97 s).

The runtime is plain C. It has a precise generational copying GC that finds roots through a shadow stack, where a liveness pass roots only references that are live across a call or an allocation. Strings are UTF-16, Haxe's semantics on HashLink. Dynamic field access uses field ids and inline caches, and exceptions use setjmp. The standard library is mostly Haxe over a few externs. That includes the regular expression engine. Some bugs found on the way:

  • __builtin_setjmp at -O2. GCC models the builtin's receiver as reachable only from the setjmp point, so a handler's load of the pending exception was hoisted above the throwing call. The fix was the real _setjmp/_longjmp, which GCC treats conservatively as returns_twice.
  • Strict aliasing. The runtime reads object slots through casts, so every build passes -fno-strict-aliasing.
  • A missing write barrier after bulk pointer moves (insert, splice, reverse, copies). An old object pointing at a young one then wasn't remembered.
  • Null<T> unary operators. !x, -x and ~x returned the unboxed value under the boxed type. GCC 14 (in cosmocc) rejected the int-to-pointer conversion, which is how we noticed.

Then came performance. The workload turned out to be memory-latency bound: a third of mapExpr's samples waited on one enum tag load. The biggest single win was making the copying collector depth-first, so an object's descendants land right after it, in the order the compiler's tree walks visit them (−15% on the self-compile). Pre-faulting the old space in 32 MB batches and a handful of smaller runtime costs did the rest.

We stopped there on purpose. The nursery and heap sizes (RT_MINOR_KB, RT_OLD_MB) stay at generic defaults instead of being tuned to this benchmark. A compiler that compiles itself is a tempting benchmark to overfit, and a backend is supposed to be good for other programs too.

8. One binary for every OS, and the browser

The same C file builds with Cosmopolitan's cosmocc into an “actually portable executable”: one file that runs on Linux, macOS, Windows and the BSDs, on x86-64 and ARM64.

The fat binary passes the full conformance suite and all macro cases. Only its x86-64 Linux half has actually been run. The ARM64 half, macOS, Windows and the BSDs are untested, and the front page says so. On the self-compile it is 5–13% slower than the glibc gcc build, which we haven't investigated yet. Later, mbedtls and libuv were patched and built with cosmocc too (libuv as a generic Unix port with a poll(2) backend, with errno codes translated at run time because Cosmopolitan's errno constants are variables), so TLS and eval.luv work in the portable binary.

For the browser, Emscripten compiles the same C to WebAssembly, with two non-obvious choices recorded in site/build.sh:

  • Compiled as C++, so RT_TRY becomes native wasm exception handling. With Emscripten's setjmp lowering, one try-heavy function grew past V8's function size limit (12 MB of wasm).
  • memory64, because the runtime lays objects out in 8-byte slots holding 64-bit pointers. That is why the playground needs a recent browser.

The first build was 7.5 MB of wasm (1.5 MB gzipped). Today's is 9.7 MB (1.9 MB gzipped), down from HL/C's 51.5 MB. It runs in a Web Worker, with a fresh instance per run. The editor is Monaco, with a Haxe tokenizer, and a second worker answers its completion, hover, signature help and go-to-definition requests through the compiler's JSON-RPC display API, the one IDEs use.

Completion only became possible once the display services were ported. test/display.py replays the upstream display test corpus against both compilers and requires identical exit code, stdout and stderr. The upstream assertions aren't evaluated, so even a case upstream marks as failing has to be reproduced. All 679 requests the test methods issue match, and so do all 7,325 requests of the extended run (every position method at every marker).

The site is static. Hosting took three tries: GitHub Pages was out because the repository is private, Cloudflare Pages was already tied to another account, so it ended up on Netlify, deploying a pre-built site-dist branch (the wasm and the APE are built here, not on the host). The downloadable haxe-in-haxe.com (23.1 MB, the binary plus a zip of the std subset it needs) is kept under the 25 MiB per-file limit that site/build.sh plans for.

9. hxc as a real target

The next step was packaging the backend for anyone's Haxe code: backend/haxelib, the hxc library.

The first version shipped the whole port as a portable binary, and the user's Haxe only ran a launcher script. It worked, but it meant typing the user's program with our compiler, without -lib support at the time. The better design came within the same hour. Let the user's own Haxe do the typing and write HXB, and let the bundled hxc.com read that archive with the ported HXB reader and emit C:

haxelib install hxc.zip
haxe -lib hxc -cp src -main Main --custom-target hxc=bin/main
./bin/main

An init macro in the library makes this one haxe call. With --custom-target hxc=<out> it asks the compiler to write the program as HXB, and after generation it runs hxc.com and the C compiler. Typing, macros, -lib and IDE support all come from the user's Haxe. Options are -D hxc.* defines: the C compiler, hxc.static for a Cosmopolitan build, hxc.ssl and hxc.uv.

Using HXB as the interchange format paid for itself straight away. It separates “does the port type correctly” from “does the backend compile correctly”, because the reference compiler can produce the backend's input. Comparing the C generated from source with the C generated from the reference's HXB found two bugs:

  • Int32 negation. int32OfString("-2147483648") negated INT_MIN after wrapping, which is +2147483648 when the port itself runs on JS.
  • The std path and DCE. DCE reruns on modules loaded from HXB and keeps every class outside the std path whole. With the bundled std at /zip/std, the user's std classes counted as user code. The tool now runs with the user's std path, and the backend built through the package gives byte-identical C to the source build.

The catch is coupling. HXB is tied to the compiler that writes it, so the user's Haxe must be the exact build hxc.com was made from. The package records it in hxc.json and names it in the error.

10. Filling in the rest of the compiler

With the core done, the remaining upstream services were translated the same way and given harnesses that compare against the reference:

  • HXB library input (hxbReader.ml). A new round-trip check reads every module of the reference's archive back through --hxb-lib and writes it again; all 275 cases round-trip identically.
  • The compilation server, its caches, and haxelib. test/server.py drives a reference server and a port server through the same scenarios (every case twice, an edit sequence whose 628 lines of verbose log must match, stdin forwarding, --next, --server-connect): 587 of 587 pass.
  • Threads in the C runtime. The server needs threads, and so do Eval programs. The first design is M:1 green threads on ucontext. Only one thread runs at a time, so the GC and runtime tables need no locks and the single-threaded hot paths stay unchanged. Threads switch when they block, sleep, wait for a descriptor, or at a minor collection. That last point caused the subtle bugs: a switch can happen inside any allocation. A lazily allocated waiter list in Mutex could lose a waiter, a Tls map could be switched out half rebuilt, and array growth reused a stale length. Each one hung the compiler's parallel filters only now and then.
  • Gc.finalise in the C GC, with OCaml's semantics: a major collection that finds the value unreachable copies it back and queues the call. HashLink has no finalisers on Haxe objects, so this is the one place the C build passes upstream's unit tests where the HashLink build can't.

Green threads give concurrency without parallelism. Upstream runs some filter passes in parallel, so OS threads in the C runtime are the obvious next step.

11. Upstream's own test suite

The conformance set covers what can be compared as HXB. The upstream repository has a much larger test suite. test/upstream.py runs the steps of upstream CI's target-independent job (tests/runci/targets/Macro.hx), in the same order, with the port on PATH as haxe, so the runners' own nested haxe calls use it too.

The first full run of the misc step failed on 64 of 686 projects. The most common cause was a single missing branch. Upstream's handle_display_after_typing aborts a compilation that already has errors before finalization. Without it, the port added follow-up errors such as “Invalid -main” after the real ones. Other finds:

  • The HashLink 2.0 JIT compiles every early-exit endtrap against the innermost trap. Leaving two nested try blocks at once therefore left the outer handler installed after its frame was gone, and the next uncaught exception jumped into a dead frame. It was found with gdb on a segfault in nullsafety, and the five affected places in the port were found by scanning the HashLink bytecode dump for consecutive endtrap false.
  • Resources were decoded as UTF-8, which lost bytes of binary resources. Path.mkdir_from_path split with a regular expression missing g. Numeric parsing needed OCaml's rules.

Exclusions apply to both compilers alike and each has a reason in the script. The projects excluded inside steps all need a target generator the port doesn't have: two misc projects compile with -js and check the JavaScript, three resolution projects run node, and one block of the sys tests builds a Neko binary. Four whole steps are skipped: source maps and an ES6 null-safety run (both JS), display (its own CI job), and the third-party projects, which are cloned from GitHub and run separately.

12. Where it stands

The benchmarks on the front page come from bench/results.json. The same compiler, built twelve ways, compiles three workloads, and a run counts only if its archive is byte-identical to the reference's:

An honest list of limits:

  • Memory. The C build uses about 1.7× the reference's peak memory on the self-compile (798 MB against 480 MB). Two likely contributors: copying collections need free space to copy into, and strings are UTF-16 (two bytes per ASCII character, where OCaml strings are bytes). The design note recommended OCaml's non-moving major heap, and the runtime doesn't have one yet.
  • No code generators. JS, C++, HashLink, JVM and the other generators aren't ported. The port type-checks, runs programs with --interp, writes HXB, and (through hxc) produces C.
  • Parallelism. Conformance runs single-threaded because the reference itself isn't deterministic under parallel filters. The C runtime's green threads don't run in parallel.
  • Portability claims are partly untested. Only Linux x86-64 has run the portable binary. The hxc target covers what the compiler needs to compile itself, not the whole language and std.
  • Small gaps are recorded in TRANSLATION.md and test/TESTING.md: the Eval debugger, memory statistics that need OCaml object sizes, IPv4-only sockets, and one-second file-time resolution on HashLink.

13. Lessons

What worked

  • A byte-identical oracle. It turned “is this right?” into a diff, and it found bugs no reasonable test would have looked for: hash iteration order, argument evaluation order, string identity. It also made every performance change safe to try, since a benchmark only counted if its output matched.
  • Translating instead of reimplementing. The hand-written start couldn't get variable ids right. The translation got all 22 members of the first fixture right on the day it could first be measured. Keeping the port traceable to upstream also made it reviewable: a disagreement with the reference meant reading two functions side by side.
  • Parallel agents with strict validation. The macro runtime, the HXB reader, the server, display, threads and the upstream suite were each worked on in separate worktrees. After each merge the suites were run again, and the results are recorded in test/TESTING.md. The merge commits record how conflicts were resolved: against upstream, not by picking a side.
  • Measuring before optimizing. Nearly every speedup in bench/README.md starts with a profile that pointed somewhere unexpected: stack capture on throws (80% of the HL/C run), closures allocated at their definition, short free runs after a sweep, an enum tag load waiting on memory.
  • Writing negative results down. The generational GC for HL/C, hx2go, chibicc, transparent huge pages: each has its numbers in the repository.

What didn't

  • Reimplementing a compiler by hand and hoping to converge on its exact output.
  • Patching other people's runtimes past a point. libhl improved a lot, but a conservative, non-generational collector stayed the ceiling. The faster answer was a runtime designed for this workload's shape.

Surprises

  • How much of a compiler's observable output depends on its implementation language's evaluation order and hash function.
  • That the ~20 s WebAssembly stall happened after the program had finished, and was caused by setjmp.
  • That the biggest single speedup of the C runtime was the order in which the collector copies objects.
  • That running a compiler this hard also finds bugs in the runtimes underneath it: a HashLink JIT trap bug, hxcpp's parallel marking, races in libhl's lazy initialisation.

The code, the notes behind every number, and the harnesses are all in the repository. The fastest way to see the result is still the playground.
